# 关键词问答（问股）技术方案

> 版本 1.2 · 2026-11-12 · 状态：**M1 后端链路与 M2 Web 化均已实施**（M1=`bebb913`，M2 验收见 §6.5）；M3 信任与兜底待做
> 产品定义与已确认决策见 [关键词问答头脑风暴](关键词问答头脑风暴.md)；本文只回答"怎么实现"。
> 实测基线：anchor = `2026-11-11T03:51:53Z`，24h 窗口 `(anchor-24h, anchor]`（左开右闭），items 251 / events 27 / themes 15（口径见 §2.1）；样本「福莱新材」（个股）与「算力」（概念题材）全链路各段用真实库数据跑通。

## 0. 结论先行

1. **链路形状**：复用现有 crawl 入库与 GLM 双模式（API / handoff），新增 ask 链路四段——①意图分析（LLM）→ ②实时爬取 + 三路检索召回（纯代码，无 LLM）→ ③关联过滤与汇聚分析（LLM，含 Top 3-5 帖全文深挖）→ ④结论呈现（Web `/ask`）。编排函数进新包 `packages/ask`；`scripts/ask.ts` 是薄 CLI 包装，与 score/write 阶段同构；Web 经 `/api/ask` resource route + SSE 驱动同一编排函数。
2. **实测定调的三条铁律**（每段设计都必须遵守）：
   - **items 为主表**：24h 内 251 条 items 仅 27 条有 event_id（**89% 无 event_id**，预筛 rejected/blocked 不进聚簇）——只查 events/themes 会漏掉约九成帖子，events/themes 只能作增强；
   - **股票标签精确匹配是主召回**：福莱新材 31 条命中中 21 条来自 `stocks_json` 精确匹配，其中 **16 条标题/摘要完全不含股名**——只做文本 LIKE 会漏一半以上；
   - **不筛 status**：31 条命中里 27 条 status=rejected（另 selected 3 / new 1，SQL 复核值，见 §2.1）——预筛状态/评分是"主题价值"轴，与"个股/概念关联度"不同轴，关键词问答对候选全集独立判断关联。
3. **头脑风暴一处假设被实测推翻**：items 摘要实为 **~250 字硬截断**（12/12 候选帖实测 247-250 字；代码上限 `EXCERPT_MAX=600` 不是瓶颈，`packages/sources/src/jiuyangongshe/parse.ts:10`——SSR 列表页本身只渲染 ~250 字）。"600 字摘要"不存在，**详情页全文抓取从 P4 增强项升级为段③标配**，且分析层对高关联帖必须输出"信息不完整"标记。
4. **最大工程坑已实测定位**，全部在召回模块程序化防护、不依赖提示词：多词 OR 缺外层括号导致窗口泄漏（实测 94 条含 63 条窗外，修正后 31）；SQLite LIKE 对 ASCII 不区分大小写（搜 'AI' 误命中 125 条英文帖）；`stocks_json` 裸 LIKE 子串误报（"东方"同时命中日出东方/东方海洋）。
5. 开放问题五项已收敛（§4），里程碑按实测基准词修订（§5）。

## 一、四段工作流逐段设计

| 段 | 名称 | 执行体 | LLM | 主要产出 | 复用核心 |

### 段① 意图分析（ask-intent）

| 项 | 设计 |
|---|---|
| 职责 | 把用户关键词翻译成检索计划：识别 kind（个股/概念题材/模糊）、给出意图假设（透明化用）、扩展词（身份词+叙事词两层）、意图股票池 |
| 输入 | 用户原始关键词；题材背景摘要——注入**窗口覆盖的北京日期集合** `{bjDateKey(window_start), bjDateKey(window_end)}`（通常 2 天，实测窗为 2026-11-10/11，对应发现 14 的两日并集口径）内 themes 的 category_label+logic 各一行（实测 themes.logic 能给主线综述，如"太空算力扩容+端侧双催化+光模块禁令转机"；themes 以北京日为主键、无精确时间戳，故按日期集合取，不用"当日"这种与 24h 滚窗冲突的说法）；`taxonomy.CATEGORIES` 的 conceptKeywords（`packages/core/src/taxonomy.ts:18`，概念词兜底扩展源，头脑风暴 E2 的三路之一） |
| 输出 | intent_json，schema 如下（扩展词分层在此承载，修正 chips 也由本段产出） |

```jsonc
// intent_json schema（TypeScript 类型据此建）
{
  kind: "个股" | "概念题材" | "模糊";
  intent: string;                                              // 一句话意图理解（段④意图假设行）
  assumption: string;                                          // 假设说明（透明化）
  expandedKeywords: { identity: string[]; narrative: string[] }; // 身份词（全称/简称/代码/别名）/ 叙事词分层——要点①的承载结构
  stocks: string[];                                            // 意图股票池，仅作路 A 精确召回输入
  altInterpretations?: Array<{ label: string; hint: string }>;  // 修正 chips 生产方：2-3 个备选意图（如"固态电池·产业催化 / ·个股名单"），段④渲染为"你是不是想问"，点击带 correction 重跑
}
```
| 生产 prompt 要点 | ① 扩展词分两层并标注：**身份词**（全称/口语简称/代码/别名）与**叙事词**（该股/该概念独占的产品叙事），词表克制——实测零命中词（"触觉手套"24h=0）不应进 SQL 主路；② 股票代码是低价值补充词（实测 605488 全库 stocks_json 0 条，24h 文本仅 1 命中且在摘要第 241/250 字符）；③ 意图股票池标注用途=仅作 stocks_json 精确召回（实测"算力"12 只意图股 7 只零命中，股票池偏"理想标的清单"而非本窗口活跃标的）；④ concept 查询建议按产业链环节（光互联/算力芯片/存储/服务器/液冷/IDC/英伟达链）配扩展词——实测该策略能补回"英伟达大跌"类召回缺口 |
| 复用点 | `chat()` + `extractJson()`（`packages/llm/src/client.ts:15,42`）；`loadPrompt("ask-intent")` 提示词外置 `industry/prompts/` |
| 降级路径 | 无 `GLM_API_KEY` → **关键词直查模式**：关键词本身 + taxonomy conceptKeywords 命中词直接进段②（意图假设行显示"关键词直查模式"）。**实施调整（§6）**：不落 ask-intent handoff 任务（避免孤儿任务占用定时 agent），API 瞬时失败同样降级直查、不阻塞链路 |

### 段② 实时爬取 + 三路检索召回（纯代码）

**②a 实时爬取（防抖）**

| 项 | 设计 |
|---|---|
| 职责 | 确保库内 24h 语料新鲜（决策：每次全量实时爬，12 板块） |
| 输入/输出 | 输入：防抖配置（`ASK_CRAWL_DEBOUNCE_MS`，默认 15 分钟）；输出：`sources.last_crawl_at` 距今 < 防抖窗则跳过爬取直接进召回，否则跑一轮全板块爬取并 upsert，统计落 `ask_results.crawl_stats_json` |
| 复用点 | 把 `scripts/crawl.ts:23-60` 的"加载 sources.json → adapter.crawl → upsertCrawledItems → 更新 last_crawl_at"抽成共享函数（放 `packages/sources/src/crawl.ts`，签名 `crawlAll(db, root, opts)`），CLI 与 web 共用一份实现，不复制粘贴 |
| 防抖与互斥 | 防抖读 `sources.last_crawl_at`（`database/migrations/0001_init.sql:9`，每次爬完在 `scripts/crawl.ts:52` 更新）；爬取互斥锁**全局**（进程内 Promise 单例 + 见 §3.4），同窗口多关键词并发只触发一轮爬取 |
| 降级路径 | 板块部分失败继续（沿用 `scripts/crawl.ts:47`"全部失败才抛"语义）；全失败 → 用库内现存量继续，结果页标注"语料截至 {MAX(published_at)}，实时爬取失败" |

**②b 三路检索召回（ask-recall，质量决定性环节）**

| 路 | 实现 | 实测依据 |
|---|---|---|
| A 股票标签精确 | `stocks_json LIKE '%“福莱新材”%'`（**必须带引号**，JSON 数组元素边界），对 intent.stocks 逐只查 | 福莱新材 21/31≈68% 主召回，16 条仅此路命中 |
| B 文本 LIKE | `(title LIKE ? OR excerpt LIKE ?)` 对全称/简称/精选叙事词逐词 OR，**整组条件强制外层括号后**再 AND 时间窗口（括号由代码生成，禁止提示词拼 SQL）；英文词改程序内大小写敏感匹配（`String.includes`）或 GLOB | “算力”概念 12 词 OR 去重 72 条（92% 召回来自此路）；不加括号实测泄漏 94 条；'AI' 裸 LIKE 误命中 125 条 |
| C events/themes 增强 | events 的 LLM 字段（title/summary/reason/tags_json）二次匹配 → `event_id` 回链 items；themes（date_key 北京日期）命中只取 `logic`/`top_stocks` 作候选帖 context 注入，**不作为独立召回源** | events 对 items 覆盖仅 27/251≈11%；但事件摘要能捞回原文用词不同形的帖（“端侧推理/token”帖被“算力”命中）；themes 粒度粗于 24h 滚窗 |

通用规则（全部实测背书）：

- **窗口**：`(anchor-24h, anchor]` 左开右闭，anchor = `MAX(published_at)` 不筛 status（数据时刻而非墙钟，代表库内语料全量）；`published_at` 为统一 24 位 ISO8601 UTC TEXT（实测 1108/1108），**字符串直接比较，不用 datetime()**；
- **不筛 status**（见 §0 铁律三）；
- **去重以 items 主键 id 为准**（形如 `jiuyangongshe:xxx`）；段间传递一律用 `items.id`，展示/外链时取 `ext_id` 列或直接用 `url` 列——实测段间 ID 口径混用（ext_id vs 主键）导致按主键查询返回空；
- **计分排序取 Top ≤15，公式逐项落死**（实测”算力”窗原配方，在该窗把 FCC 光模块簇、太空算力、华为存储、FPGA 算力等核心叙事稳定排前）：`score = 标题命中词数×3 + 摘要命中词数×1 + 意图股票标签命中×2 + 事件/主题回链×1.5 + (status='selected' ? 1 : 0) + 0.1×min(score_avg, 5)`。两处如实标注：末项 `min(score_avg,5)` 为实测原文口径（score_avg 为 0-100 分制，该上限使末项 ≤0.5，疑为笔误，M1 校准时以回归基准复核后定稿为 `0.1×min(score_avg,100)` 量级）；加帖型降权 ×0.5、多股简报帖（路 A 且标签 >5 且与文本零交集）×0.3 为 **M1 默认待校准参数**（实测仅给出降权方向未定值）；
- **加帖型降权不剔除**：标题正则 `(盘前|早报|简图|复盘|资讯精选|涨停解析)` 降权（实测盘前早报类标题常带词但信息密度低；英伟达暴跌这类总锚动态同簇保留一条）；
- **多股简报帖防污染**：路 A 命中帖若 stocks_json 标签数 > 5 且与路 B 文本命中零交集 → 降权（实测路 A 独有的 4 条全是盘前简报类噪声）；
- **撞名防护**：对 2 字口语简称（如“福莱”）常规核查同首词公司（福莱特实测 24h 三字段 0 命中，本例干净），命中数异常放大时用带引号 stocks_json 精确过滤兜底；
- **每词带命中数**：扩展词先逐个 COUNT（24h/7d），零命中词不进 SQL 主路，词表瘦身结果记入 `recall_json`。

| 项 | 说明 |
|---|---|
| 输出 | 候选 ≤15 帖（id/title/excerpt(250 字真实值)/stocks/score_avg/status/event_id/url/published_at）+ 各路命中统计，落 `ask_results.recall_json` |
| 复用点 | `packages/core` db/repos；taxonomy conceptKeywords；无 LLM，**无 handoff 需求** |
| 降级路径 | 三路并集（去重后）= 0 才触发扩窗（低命中 ≠ 无命中，并集 ≥1 不扩）：先 48h 再 72h 各重跑一次召回，命中则正常出结果并在结论卡标注"已扩窗至 48h/72h"；72h 仍 0 → status=empty 出"无命中"结果页（附 taxonomy 最近似题材卡 + 扩窗过程透明展示）。阈值即"并集=0"，无中间阈值；M1 验证词见 §2.3 |

### 段③ 关联过滤与汇聚分析（ask-aggregate，R1/R2 最多 2 次调用）

| 项 | 设计 |
|---|---|
| 职责 | 对候选全集独立判断关联 → 按事件/话术聚类去重 → 抽取合并要点 → 结论与缺口。**调用拓扑固定（最多 2 次调用）**：R1 = excerpt 级全候选，一个 prompt 同时做关联判定+汇聚+产出深挖名单（实测该形态质量达标，候选 ≤15 帖上下文足够，不按"关联/汇聚"功能拆分）；随后全文抓取（无 LLM）；R2 = 同一份 prompt、深挖帖输入替换为全文后重跑，产出最终 result_json；**深挖名单为空则跳过 R2，R1 结果即终稿**。handoff 阶段名统一 `ask-aggregate`，batch 后缀 `_r1`/`_r2` 区分两轮 |
| 输入 | 候选帖全集 + intent 假设 + 路 C 注入的 events/themes context（催化 logic、top_stocks，附字段语义说明）；R2 轮对深挖帖以 item_details.content 替换 excerpt |
| 输出 | result_json，schema 如下（要点②⑤的"信息形态/主客体/信息不完整"均有对应字段，TypeScript 类型据此建） |

```jsonc
// result_json schema（R1 增产 detailIds；R2 落全量）
{
  keyPoints: Array<{
    point: string;
    sourceIds: string[];                                  // items.id（段间统一主键口径）
    mergedFrom?: string;                                  // 事件/话术去重说明（哪些帖合并、依据）
    form: "A" | "B";                                      // A=主标的直接资讯；B=以主标的为锚的映射帖（要点②）
    subjects?: string[];                                  // B 类必填：帖主推标的（主客体标注）
    infoLayers: Array<"事件" | "研报观点" | "UGC推测">;    // 信息分层（要点④），无出处数字不得进 timeline
    infoIncomplete?: boolean;                             // excerpt 截断丢关键信息（要点⑤）→ 进深挖名单
  }>;
  relatedStocks: Array<{ name: string; reason: string }>;
  timeline: Array<{ time: string; text: string }>;         // time = 北京时间展示串（库内 UTC +8）
  conclusion: string;                                      // ≤120 字
  gaps: string[];
  rejected: Array<{ id: string; reason: string }>;
  detailIds?: string[];                                    // 仅 R1 产出：深挖名单（Top 3-5 的 items.id）
}
```
| 生产 prompt 要点 | ① **不信任上游 status/score**：独立判断关联（实测 12 候选中 10 条 rejected 但个股强关联，含全窗唯一代码命中帖与最量化测算帖）；② **关联分两类并强制标注主客体**：A=主标的直接资讯（点名/标签/代码/正文），B=以主标的为锚的映射/对标帖——实测最高价值帖多为 B 类（以福莱为锚的空间测算帖），按"蹭热度"误杀会丢关键信息；只有"标签共现且无任何增量"判无关（实测两样本各仅拒 1 帖）；③ **先事件聚类、再抽时间线、后抽个股**：同源转发帖（实测同一 FCC 事件 4 帖、同一电报 3 帖逐字转述）合并，keyPoints 按事件合并 sourceIds 并在 mergedFrom 写明去重逻辑；④ **信息分层**：每个要点标 [事件/研报观点/UGC推测]，无出处数字不得进 timeline（实测荐股话术"千亿市值空间"、无出处"AI 服务器出货年增 28%"混在事实里）；⑤ **excerpt ~250 字截断**：对截断处丢失关键信息的帖输出"信息不完整"标记并列入 Top 3-5 全文深挖名单；情绪话术（"妖者五倍起"）作风险提示素材不作事实引用；⑥ **时区**：timeline 用北京时间（库内 UTC +8，实测不复盘帖会错显示为上午）；⑦ 引用 themes.top_stocks 必须附 score/mentions 语义（实测 sentiment 主题 5 股同分 247 是事件级均分，非个股情绪领先） |
| 全文深挖（段③.5，= R1→R2 之间的无 LLM 环节） | 深挖名单取 R1 产出的 `detailIds`（infoIncomplete 帖 + 高关联 Top 3-5）按 `items.url` 抓 `/a/{extId}` 全文（新 `fetchDetail`，§3.5），回填 `item_details` 缓存后作为 R2 轮输入；抓取失败用 excerpt 继续并记 gap（名单为空则无 R2） |
| 复用点 | handoff 双模式同 score（`scripts/score.ts:98-171` 结构照搬）；`buildPrompt`（`packages/llm/src/prompt.ts:10`） |
| 降级路径 | LLM 失败 → handoff 落盘 `ask-aggregate-*.json`；全文抓取失败 → 继续用 excerpt；候选为空 → 直接进段④空结果兜底 |

### 段④ 结论呈现（/ask 页）

| 项 | 设计 |
|---|---|
| 职责 | 结论先行渲染 + 进度可视化 + 信任要素（证据链/意图透明/可修正） |

### 3.2 ask_results / item_details 表（0003_ask.sql）

```sql
-- 关键词问答：一次查询一行，存完整中间产物（开放问题 2 的答案：存，便于复盘调 prompt）
CREATE TABLE IF NOT EXISTS ask_results (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  keyword TEXT NOT NULL,                 -- 用户原始输入
  keyword_norm TEXT NOT NULL,            -- 归一化（去空白/全角→半角/小写），单飞锁键
  kind TEXT,                             -- 个股 | 概念题材 | 模糊（段①产出）
  status TEXT NOT NULL DEFAULT 'running',-- running | awaiting_handoff | done | empty | failed
  phase TEXT NOT NULL DEFAULT 'intent',  -- intent | crawl | recall | aggregate | detail | answer（与 §3.3 SSE 事件一一对应）
  window_start TEXT NOT NULL,            -- (anchor-24h, anchor] 左开右闭，UTC
  window_end TEXT NOT NULL,
  crawl_stats_json TEXT,                 -- 段②a：防抖命中与否 / 板块统计
  intent_json TEXT,                      -- 段①产物
  recall_json TEXT,                      -- 段②b：各路命中数 / 词表瘦身 / 候选 id
  detail_ids_json TEXT,                  -- 段③.5：抓全文的 item id 列表
  result_json TEXT,                      -- 段③④产物（keyPoints/relatedStocks/timeline/conclusion/gaps/rejected）
  error TEXT,
  created_at TEXT NOT NULL,
  finished_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_ask_results_kw ON ask_results(keyword_norm, created_at DESC);

-- 帖子全文按需缓存（SSR 摘要仅 ~250 字，实测不足；抓过一次不再重抓）
CREATE TABLE IF NOT EXISTS item_details (
  item_id TEXT PRIMARY KEY REFERENCES items(id),
  content TEXT NOT NULL,
  fetched_at TEXT NOT NULL,
  fetch_error TEXT                       -- 失败也留行，防止反复重抓；NULL=成功
);

-- M3 假设指标埋点（web 现无 analytics 设施，最小自研：/ask 页 click 委托 + fetch keepalive POST /api/ask 的 action 落此表）
CREATE TABLE IF NOT EXISTS ask_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ask_id INTEGER NOT NULL REFERENCES ask_results(id),
  type TEXT NOT NULL,                    -- view | source_click | chip_click
  target TEXT,                           -- 点击的 sourceId / chip label；view 为空
  ts TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_ask_events_ask ON ask_events(ask_id, type);
```

**running 行超时回收**：任一新查询或 watch 轮询发现 running 行 `created_at` 距今 > `ASK_STALE_MS`（默认 30 分钟；单次链路预估爬取 ~1 分钟 + LLM 数十秒，30 分钟宽裕）→ 置 `failed`（error='stale: 超时回收'），watch 模式据此发 error 事件，同词新查询新开行（不复活 stale 行，窗口 anchor 已过期）；`awaiting_handoff` **不回收**（等待人工回填，无超时），结果页标注滞留时长。

### 3.3 /api/ask resource route + SSE

- 路由注册：`route("api/ask", "routes/api.ask.ts")`（React Router v7 resource route，无默认导出）：**loader 出 SSE 流，action 收埋点**（POST body `{askId, type, target}` 落 ask_events）。
- 请求：`GET /api/ask?q=<关键词>[&watch=<ask_results.id>]`。EventSource 只支持 GET，参数走 query string。
- **phase 枚举与事件一一对应**（`intent | crawl | recall | aggregate | detail | answer`，即 ask_results.phase）；前端进度条仍为头脑风暴 D2 的五步文案，映射：理解意图←intent、实时抓取←crawl、关联筛选←recall+aggregate、全文深挖←detail、综合结论←answer。事件全集：
  ```
  event: stage  data: {"phase":"intent","message":"意图分析中…"}
  event: stage  data: {"phase":"crawl","message":"实时爬取 12 板块（防抖跳过）","boards":[…]}
  event: stage  data: {"phase":"recall","message":"三路召回 31 → 候选 12"}
  event: stage  data: {"phase":"aggregate","message":"关联过滤与汇聚分析（R1 excerpt 级）…"}
  event: stage  data: {"phase":"detail","message":"深挖 3 帖抓全文…"}
  event: stage  data: {"phase":"answer","message":"综合结论（R2 全文级）…"}
  event: ping   data: {"ts":"…"}                     ← 心跳，每 15s 一次
  event: pause  data: {"phase":"intent","tasks":["ask-intent-20261111_01.json"]}
  event: done   data: {"resultId":17}
  event: error  data: {"message":"…"}                 ← 含 stale 超时回收（§3.2）
  ```
- 首次请求：归一化关键词 → 查单飞锁（模块级 Map，键=keyword_norm）→ 命中则转 `watch` 模式附流；未命中则 INSERT ask_results(status=running) 并在后台跑 `runAsk()`，loader 返回 `text/event-stream`，`runAsk` 的 onProgress 回调逐 phase 转发 stage 事件。
- **awaiting_handoff**：管线跑至需 LLM 处且无 `GLM_API_KEY` → 发 `event: pause`（含 phase 与待回填任务文件名）后关流；agent 回填并 `npm run ask -- --consume` 后，前端重新 `watch` 同一 ask_id 续跑。
- **watch 模式**（断线/刷新/handoff 等待）：不重跑管线——loader 每 5s 读该 ask_results 行（phase/status 变化时发对应 stage 事件），每 15s 发 ping 保活；行至 done/empty/failed 发对应终态事件后关流。前端 EventSource `onerror` 后 30s 退避重连带 `watch=<id>`。
- 单进程假设：web 以 `react-router-serve` 单进程跑（现状），模块级 Map 即全局锁；多实例部署时改用 ask_results 行级锁（INSERT ... WHERE NOT EXISTS running 同词行）。

### 6.2 与原设计的三处偏差（均有意为之）

1. **ask-intent 不落 handoff 任务**：无 key 时意图段直接走关键词直查模式（原设计还要求落盘任务）。原因：意图任务被回填后无处可应用（直查已产出结果），只会制造孤儿任务占用定时 agent。ask-aggregate 的 handoff 不受影响（它才是必须等 LLM 的段）。
2. **详情页解析改为 NUXT 载荷求值**（见 §3.5）：原设计假定 SSR DOM 有正文容器，实测为 CSR，正文在 `window.__NUXT__` 载荷。`node:vm` 沙箱（无 require/process、3s 超时）求值，选择器路径集中 `DETAIL_PAYLOAD`。
3. **基准逐词口径澄清**：`ask-m1-baseline.json` 的 `perWordCounts` 实为**标题/摘要/stocks_json 三字段 OR LIKE** 口径（基准复核时"三字段"未显式写明）；`recall()` 的 `perWord` 是两字段、ASCII 大小写敏感口径。回归脚本按口径分层对齐，不算实现偏差，记录在此防未来误读。

### 6.4 CLI 用法
